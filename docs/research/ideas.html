High-Level Plan

Read the cards through this lens: first build the measurement set, then retrieve candidates, then score and explain them, then test advanced challengers only when they beat the baseline.

Step 1

Build The Gold Set

Why?

Without labels, every matcher looks better than it really is. The first job is to create known true/false pairs so we can measure recall, precision, false positives, and false negatives.

From / Options
From synthetic traveler records, controlled corruptions, small public samples, OpenSanctions Pairs for learning/benchmarking, and any later properly licensed/program-approved gold labels.
Output
A versioned evaluation set with slices plus M26 prior-shift views: transliteration, DOB errors, document conflicts, common names, rare names, missing fields, cross-script names, and expected alerts per million.
Step 2

Find Candidates

What are the options?

Given one person, retrieve the most plausible records from a large population before scoring. Start with OpenSearch/Postgres/Solr-style retrieval, then compare fuzzy, phonetic, vector, and graph-assisted expansion.

From / Options
M21/M22 are the main lane. M25 is the research lane for graph-assisted retrieval.
Output
Recall@10/50/100, candidate volume, latency, and a log explaining why each candidate was retrieved.
Step 3

Score And Explain

What happens after retrieval?

Each candidate pair gets scored using name similarity, DOB/document/country evidence, rarity weights, transliteration normalization, and learned scoring. The reviewer sees a waterfall explanation, not just a black-box score.

From / Options
M01/M03/M04/M06/M10/M11/M29 form the main scoring path. M27 is a stronger transformer challenger after the baseline exists.
Output
A candidate list with calibrated scores, reasons, conflicts, recommended review priority, and recall-at-fixed-precision metrics.
Step 4

Run Challenger Lanes

Where do advanced ideas fit?

Once the baseline exists, test optional challengers against the same gold set: LLM failure-type review, conformal abstention, GNN reranking, graph-assisted retrieval, hard-positive and hard-negative mining, active learning, and cluster consistency checks.

From / Options
M12/M13/M15/M20/M23/M24/M25/M27/M28/M30 are challenger lanes. They do not replace the baseline unless they beat it.
Output
A champion/challenger board showing incremental true positives, new false positives, lost true positives, and which slice improved.
Step 5

Package The Brief

What do we show at the end?

The end product is not just code. It is a working demo plus evidence that the approach beats a baseline and that each optional idea has a measured reason to exist.

From / Options
M05/M16/M19/M26 define the reporting and operating cadence.
Output
Demo, metrics report, base-rate alert-volume report, slice analysis, data provenance, risk guardrails, and a recommendation on what to build next.

M01 Core
BUILD FIRST

Name-First Triage with Secondary-Evidence Scoring

Keep name similarity as the anchor; score every supporting field as a structured contributor in a transparent waterfall, not a brittle pass/fail rule.

What we do

Score one possible match using names plus secondary evidence.

Why it matters

Names alone create too many false alarms and miss hard variants.

Value

Reviewers see a clear, field-by-field reason for each score.

Why interesting

This is the difference between a fuzzy-string toy and real screening. Secondary identifiers are never guaranteed complete or correct, so they must strengthen or conflict with a name match rather than gate it.

Potential impact

Cuts false positives without hiding why someone was flagged or cleared, and directly attacks the common-name alert flood.

Demo path

Synthetic/public pair set; each pair gets a waterfall: name weight, DOB agreement, passport-country agreement, citizenship, conflict penalty, final disposition. Interactive scorecard degrades as fields drop out.

Open-source path

Splink waterfall charts and term-frequency adjustments; recordlinkage comparisons; RapidFuzz/jellyfish for name similarity.

Enterprise path

AWS Entity Resolution or SageMaker/DataRobot field-aware classifier later; first demo stays local and explainable.

Risk / guardrail

Secondary identifiers can be wrong. Treat conflicts as evidence, not automatic elimination, unless policy says otherwise.

M02 Synthetic Data
BUILD FIRST

Synthetic Traveler Lab + Controlled Corruption

Build a synthetic identity generator that emits records with labeled corruptions and known true/false match IDs.

What we do

Create fake-but-realistic records where we know the right answer.

Why it matters

We need labeled examples before we can measure anything honestly.

Value

Gives us a safe regression set for typos, transliteration, DOB errors, and missing fields.

Why interesting

No synthetic gold means no training data, no benchmark, no learned scorer. A reproducible synthetic lab sidesteps provenance problems while making error modes visible.

Potential impact

Turns vague quality claims into diagnostics such as recovery by transliteration, DOB transposition, dropped surname, or missing field.

Demo path

Generate around 500 synthetic identities with controlled corruptions and known true IDs; add a corruption-dial UI showing matcher accuracy degrade by corruption type.

Open-source path

Faker, FEBRL concepts, custom generator, NetworkX for synthetic co-travel edges.

Enterprise path

Permanent regression suite gating every future matcher release.

Risk / guardrail

Synthetic data is too clean by default. Deliberately inject missingness, conflicts, cultural name variation, and inconsistent transliteration or the numbers will lie.

M03 Learning
BUILD FIRST

Gold-Positive Learned Scorer

Train a classifier on proven true positives so the model learns real matching behavior, including pairs where names are not visually close because stronger identity evidence proves identity.

What we do

Train a simple model on known true/false pairs.

Why it matters

Rules are a baseline; learned scoring can use many weak signals together.

Value

Produces calibrated scores we can compare against the baseline.

Why interesting

This is the core strategic opportunity. OpenSanctions already demonstrates a production baseline using logistic regression on entity fields; the benchmark paper reports 91.33% F1 for that baseline and higher LLM challengers.

Potential impact

Turns adjudication history into a measurable, calibrated model instead of tribal knowledge. Calibrated probabilities enable defensible thresholds.

Demo path

Train logistic regression and gradient boosting on OpenSanctions Pairs or synthetic gold; compare against rules-only; show SHAP attribution per decision.

Open-source path

scikit-learn, XGBoost, Splink feature exports, nomenklatura regression model as reference, Zingg labeling concepts.

Enterprise path

SageMaker/DataRobot with monitored training, drift reports, threshold governance, retrained on properly licensed/program data.

Risk / guardrail

Gold is only gold if the source is trustworthy; historical decisions encode bias/policy drift. Avoid leakage: do not train on the same strong identifier you are predicting from. M26 Benchmark
BUILD FIRST

Base-Rate / Prior-Shift Evaluation

Evaluate every matcher under realistic deployment base rates, not only balanced pair distributions, because precision is base-rate dependent and balanced benchmarks systematically overstate it.

What we do

Re-score models when true matches are rare.

Why it matters

Balanced benchmarks overstate precision in real screening.

Value

Shows expected alert volume and precision before deployment surprises.

Why interesting

OpenSanctions Pairs and most ER benchmarks are roughly balanced. Real screening is closer to a rare-match haystack. False positives scale with the size of the negative class, so the headline F1 from a benchmark paper does not transfer cleanly to deployment.

Potential impact

Turns optimistic benchmark numbers into honest operating numbers, makes threshold selection defensible, and shows expected review volume before anyone is surprised in production.

Demo path

Take the trained scorer from M03, hold the gold labels fixed, then resample evaluation across base-rate sweeps such as 1:100, 1:10k, and 1:1M. Plot precision, recall, and expected reviewer alert volume at each prevalence and fixed threshold; show the precision cliff and the threshold needed to hold a target review budget.

Open-source path

scikit-learn metrics with stratified resampling; precision-recall under prior correction; simple Monte Carlo over M21/M22 candidate-retrieval output.

Enterprise path

Standing prior-shift report in the M19 board, with threshold governance tied to a declared review-capacity budget.

Risk / guardrail

Resampling assumes score distributions are stable across prevalence. Validate against the true retrieval-stage negative distribution from M21/M22, not synthetic negatives only. Report assumed base rate with every precision number.

New Area - Candidate Retrieval at Scale

Find the plausible candidates first. This is the open-source replacement lane for Elasticsearch-style lookup over millions of records.

M21 Search / Blocking
BUILD SUPPORT

Open Candidate Retrieval Layer for 7M-Record Search

Separate candidate retrieval from final matching: use open-source search/blocking indexes to turn one person query against 7 million records into a small candidate set for the scorer.

What we do

Find the small set of plausible records before scoring.

Why it matters

At millions of records, pairwise scoring everything is impossible.

Value

Turns one-person lookup into top-K candidates the scorer can handle.

Why interesting

Pairwise matching is useless if the system cannot find plausible candidates quickly. The retrieval layer should use DOB, document IDs, country fields, phonetic/name keys, n-grams, and alias fields to reduce 7 million records to top-K candidates before M01/M03 score them.

Potential impact

Replaces proprietary Elasticsearch dependency in the prototype path and makes the August demo more operationally realistic: query one person, retrieve candidates, score, explain, and compare to baseline.

Demo path

Index synthetic/public records at 7M-scale or sampled scale; enter one person; show retrieval passes: exact document/DOB filters, phonetic or n-gram name search, alias expansion, top-K candidate list, then final score waterfall.

Open-source path

OpenSearch for closest Elasticsearch-style replacement; Apache Solr/Lucene for mature open search; PostgreSQL pg_trgm for a simple local SQL lane; Typesense/Meilisearch for lightweight typo-tolerant prototypes.

Enterprise path

Candidate-retrieval service with index governance, query audit, latency SLOs, and A/B comparison against the current Elasticsearch baseline.

Risk / guardrail

Retrieval mistakes create invisible false negatives. Never rely on one strict filter. Use multiple retrieval passes, union candidate sets, log why each candidate was retrieved, and measure recall-at-K against gold data.

M22 Search / Blocking
BUILD SUPPORT

Multi-Pass Blocking Cascade: Exact, Fuzzy, Phonetic, Vector

Use a cascade of cheap-to-expensive retrieval passes: exact document/DOB matches first, then DOB-year/name keys, phonetic aliases, trigram/fuzzy search, and optional vector search for hard name variation.

What we do

Use several retrieval passes instead of one fragile search.

Why it matters

Exact document, DOB, fuzzy name, phonetic, and vector methods catch different cases.

Value

Improves recall while keeping candidate volume measurable.

Why interesting

A single query strategy will miss people. Document filters are precise but brittle; DOB is strong but dirty; names are noisy; embeddings can help but should not own the whole retrieval problem.

Potential impact

Improves recall at practical latency by giving each signal a chance to retrieve candidates while keeping the expensive scorer focused on a small set.

Demo path

Show a Sankey-style funnel from 7M records to candidate sets by pass: document hit, DOB+surname block, DOB-year+phonetic block, trigram name hit, vector hit. Then report recall@10, recall@50, and candidate volume.

Open-source path

Splink/recordlinkage blocking rules, Postgres B-tree plus pg_trgm indexes, OpenSearch/Solr filter queries, Qdrant/OpenSearch k-NN for optional filtered vector retrieval.

Enterprise path

Retrieval playbook with pass-level metrics, per-pass latency, pass-level false-negative audits, and promotion rules for new retrieval passes.

Risk / guardrail

Too-loose retrieval floods the scorer; too-tight retrieval misses true matches. Track marginal candidates and marginal true positives per pass, then prune passes that add noise without recoveries.

Agreement on rare tokens is stronger evidence than agreement on common tokens; near-misses on rare tokens deserve review.

Potential impact

Improves precision on common names and triage on rare-name collisions.

M29 Name Intelligence
HIGH VALUE

Transliteration & Romanization Normalization

Make script normalization a first-class measured pipeline stage feeding every matcher, rather than an implicit assumption buried inside cross-script rule routing.

What we do

Normalize names across scripts before matching.

Why it matters

Raw spelling misses romanization and transliteration variants.

Value

Improves cross-script recall for every downstream matcher.

Why interesting

Transliteration is foundational. The same Arabic, Cyrillic, or CJK name can romanize many ways across sources; without a normalization stage every downstream matcher inherits that inconsistency.

Potential impact

Cheap, broad recall improvement on the cross-script slice, plus a clean ablation showing lift attributable to normalization alone.

Demo path

Run the cross-script slice through uroman/ICU romanization plus a learned transliteration-variant option. Compare matcher recall with normalization on versus off, report per-script lift, and show any precision cost from over-collapsing distinct names.

Open-source path

uroman, ICU4C/PyICU transliteration, unidecode as a weak baseline, optional learned transliteration variants from M02 synthetic corruptions.

Enterprise path

Shared normalization service with per-script versioning and a normalization-quality dashboard.

Risk / guardrail

Aggressive normalization can collapse genuinely different names. Keep original strings as parallel features, never discard them, and measure precision cost per script.

M27 Advanced / Learning
RESEARCH

Cross-Encoder Name Matcher

Fine-tune a small multilingual cross-encoder that takes a name pair plus minimal allowed context and outputs a calibrated match probability.

What we do

Train a compact transformer to score two names together.

Why it matters

Cross-encoders model interactions that bi-encoders and string metrics miss.

Value

A strong challenger between cheap string scoring and expensive LLM reasoning.

Why interesting

Bi-encoders are useful for retrieval because they encode each name independently, but a cross-encoder scores both names together and can model token interaction directly. It is the modern middle ground between cheap string metrics and full LLM reasoning.

Potential impact

A calibrated learned scorer could lift hard cross-script, transliteration, nickname, and token-order cases without the cost and governance burden of a general LLM.

Demo path

Fine-tune a MiniLM, char-aware, or multilingual cross-encoder on OpenSanctions Pairs, M02 synthetic gold, and M28 hard negatives. Compare against logistic/XGBoost and M09 bi-encoder on recall-at-fixed-precision; calibrate the output and test whether attention or feature attribution can support M04 explanations.

Open-source path

Sentence Transformers cross-encoders, Hugging Face transformers, char-level or byte-level multilingual backbones, scikit-learn calibration.

Enterprise path

Distilled or quantized cross-encoder served behind the candidate-retrieval or gray-band queue, versioned in a model registry with drift tracking.

Risk / guardrail

Easy to leak strong identifiers into the text input. Restrict to name plus minimal allowed context, hold out by source/time, and use only as a reranker over retrieved candidates because it is too slow for all-pairs search.

What we do

Use a GNN to rerank candidate match edges.

Why it matters

Graph neighborhoods may reveal evidence a pairwise row cannot see.

Value

Tests whether graph context improves gray-band true-match recovery.

Why interesting

This is the cleanest GNN touchpoint because it turns ER into link prediction. Potential impact

Potentially improves gray-band recall and reduces false positives where pairwise scores are ambiguous but graph context is informative. The practical win would be finding true matches just below the baseline threshold without flooding reviewers.

Demo path

Enterprise path

Strategic Answers

How to separate near-term prototype work from research bets and governance-gated ideas.

01

Strongest 3-5 for an open-source/local, name-first prototype

Build the spine in order: M02 synthetic gold, M01 evidence stack, M03 learned scorer, M04 explanations, M05 benchmark lane, and M26 base-rate evaluation. Add M21/M22 as the candidate-retrieval layer for realistic 7M-record lookup, plus M06/M29 for the cheapest high-value name upgrades.

02

Too risky, speculative, or sensitive-data-dependent

M17 travel-party and M18 biometric-label concepts require lead/compliance posture before any build. M09 embeddings, M23/M24/M25 GNN work, and the collective half of M14 are high-ceiling research bets. OpenSanctions non-commercial licensing is a near-term risk to actively manage.

03

Evaluation design that makes the strong ideas credible

Use OpenSanctions Pairs plus synthetic gold, then apply M26 prior-shift evaluation. The primary operating metric should be recall at fixed high precision, or review-volume at fixed recall. F1 stays as a secondary paper-comparison metric. Slice by name group, script, corruption type, retrieval lane, and sprint target.

04

Using gold positives without overfitting to historical bias

Tier labels by provenance, hold out by time and source, audit label provenance, measure inter-annotator agreement, slice errors by name group/script, keep humans on disposition, and avoid leakage from strong identifiers used as labels.

05

Additional public/open datasets and benchmarks

OpenSanctions Pairs, OpenSanctions API, OFAC SDN, Consolidated Screening List API, SSA baby names, US Census surnames, GeoNames, FEBRL, DBLP-ACM/Amazon-Google, Wikidata aliases, nickname/diminutive datasets, nomenklatura training data and regression model.

06

Near-term prototype vs later enterprise-grade

Near-term: M01-M05 plus M26, M21/M22 for candidate retrieval, M06/M29, M07 light, M08, M11, M13/M28, M15, M16, and M19 as the operating cadence. M20/M30 are controlled stretches after the baseline exists. Research: M09, M27, M23/M24/M25 GNN work, and collective M14. Enterprise/governed: M03 under SageMaker/DataRobot, M14 graph platforms, M17 after policy review, M18 under biometric governance.

07

Biweekly algorithm customization cadence

Every two weeks, choose one target failure slice, write the hypothesis before coding, implement one candidate matcher change, and compare it against the frozen baseline on gold data plus newly adjudicated inflow. The review board should show baseline beat/no-beat, net-new true positives, new false positives, lost true positives, alert-volume delta, and whether the candidate should ship, hold, or become a research branch.

08

Where LLMs fit without taking over matching

Use LLMs on pre-registered failure types or M30 conformal abstentions, not as a generic judge. Clear matches and clear nonmatches should stay with cheaper deterministic/probabilistic methods. Higher-leverage LLM uses include alias/transliteration variant generation, hard-negative generation, and feature-grounded explanation drafts constrained to actual evidence.

09

Open alternatives to Elasticsearch-style candidate search

Treat this as candidate retrieval, not final matching. OpenSearch is the closest open Elasticsearch-style path; Solr/Lucene is mature and Apache-licensed; Postgres with pg_trgm is a strong local/simple prototype lane; Typesense or Meilisearch can support lightweight typo-tolerant demos; vector stores such as Qdrant belong only where embeddings add recoveries. Whatever engine is used, measure recall@K and false-negative misses before scoring.

10

Where GNNs fit without derailing the project

Use GNNs as a challenger around retrieval and graph consistency, not as the core matching spine. M25 is the candidate-retrieval version: seed with normal search, expand through an evidence graph, and measure incremental recall@K. M23 reranks candidate edges and M24 detects bad cluster bridges. All three must beat simpler baselines before they become more than a research track.
